In most related work, only the indirect radiance component is cached or
approximated by a neural network, while direct radiance is computed exactly using
Monte Carlo integration. We use the same approach. Because VPT does not natively 
support separating these components, we rework its path tracing logic. Following
\cite{bauer_photon_2024}, we split the computation into three separate shaders:
\begin{itemize}
    \item \emph{Sample generation.} Perform delta tracking until a scattering
    or an absorption event occurs. This gives us a sample in which we hit
    the volume.
    \item \emph{Direct radiance.} Starting at the generated sample, perform
    delta tracking until we either hit a light or the photon is absorbed. In
    the case of scattering, the ray is discarded because it is not regarded as
    single scattering anymore.
    \item \emph{Indirect radiance.} As with direct radiance, perform delta
    tracking but allow scattering events and discard rays with fewer than two
    bounces, i.e., real scattering events, when hitting a light.
\end{itemize}
\Cref{fig:scattering} illustrates these shaders for a single sample. Once the
direct and indirect radiance have been computed, a separate shader \emph{composes}
them into global illumination by taking their average, weighted by the number of 
direct and indirect samples. When the \emph{accumulate} option is enabled, all
three illumination components (global, direct, and indirect) are additionally
accumulated over successive frames, each independently of the others. During evaluation, this design made it possible to produce images of all three
components, visible in \Cref{fig:illumination}, in a single experiment and to 
switch between them without restarting the computation.

We also rework the logic for handling iterations. Previously, if the maximum
number of bounces was not reached within the current iteration, VPT would
continue the path in the next iteration, i.e., the next frame. We change this
so that each path is computed from start to finish within a single iteration.
This change allows us to introduce an additional parameter, \emph{samples},
which controls the number of photons traced per pixel.

\section{Ground truth}

As we already compute indirect radiance when rendering the image, a separate
pass to generate ground truth data for the model is not needed. Reusing these
values means the model will learn to predict the radiance values needed for the
current camera angle. Since there is enough data available in each frame, we
store only the first valid sample out of \emph{samples} rays sent per pixel.

For each sample, we store the value either when an absorption event occurs, in
which case the radiance is zero, or when we hit the scene boundary after at
least two real scattering events. In the latter case, the radiance is the 
transmittance multiplied by the environment sample, which is uniform white light
in our setup, so the final stored value is just the transmittance.

For each pixel, we store eight values in a \ac{gpu} buffer: the position
$(x, y, z)$, the sample’s direction azimuth and elevation $(\varphi, \theta)$,
and the radiance $(r, g, b)$. Note that the position and direction are taken
from the start of the path, i.e., from the sample generated by the sample
generation shader, not from the last ray position. For a $512 \times 512$ image,
this amounts to $\qty{8}{\mega\byte}$ of data per frame.

Before this data can be used, it must be copied from the \ac{gpu} to main memory.
We do this using asynchronous mapping in WebGPU. This copying can take multiple
frames, in which case we drop data until the copying is finished. After the data
is available, we either add it to a ZIP archive as a binary file or send it to our
training server. Using a ZIP archive, we can download $\qty{4}{\giga\byte}$ of
data, which is useful during development and later for repeatable evaluation
experiments.

\section{Radiance Field Network}

Our neural network model, \emph{Radiance Field Network}, is based on the
Photon Field Network model from~\cite{bauer_photon_2024}. We modify the model
for our input data and for running it in a browser. Because our data are
generated for a specific renderer configuration, we drop the coefficient $g$,
which is constant. Position and direction are still encoded using
Multiresolution Hash Encoding from~\cite{muller_instant_2022}, but we remove the
log transform of the output because we do not observe any improvement in our
results. Instead, we clamp the output to the interval $[0, 1]$. The
architecture diagram is shown in \Cref{fig:arch}.

The position and direction vectors have separate encoding blocks. Each block
contains $L$ levels, and each level outputs an $F$-dimensional embedding. The
levels span resolutions from $N_{\min}$ to $N_{\max}$ as follows:
\begin{align}
    b &= \exp\left( \frac{\log N_{\max} - \log N_{\min}}{L - 1} \right), \\ 
    N_l &= \left\lfloor N_{\min} \cdot b^l \right\rfloor.
\end{align}
On each level, we first find the corners of the voxel containing the input
vector. These corners are hashed to obtain indices, which are then used to
retrieve embeddings from the table with maximum size $T$. These embeddings are
linearly interpolated in proportion to the distance between the input vector
and the voxel corners. All embeddings are then concatenated.

In our case, we use
$L = 11$,
$F = 4$,
$N_{\min}^{\text{pos}} = 8$, $N_{\max}^{\text{pos}} = 128$,
$N_{\min}^{\text{dir}} = 16$, $N_{\max}^{\text{dir}} = 64$,
and $T = 2^{18}$. All of these values, along with $3$ fully connected layers
of size $16$ to produce the final output, were selected using an automatic 
Bayesian hyperparameter search.

The model is optimized with the Adam optimizer, using a learning rate of $0.01$
and an MSE loss function. Because the model is intended for use in an online
setting, we train it for a single epoch.

\section{Training server}

To use our model during rendering, we have to train it in an online setting.
Offline training would require waiting until the model is fully trained, whereas
online training makes it possible to start generating images while the model is
still being trained in the background. There are not many deep learning libraries
available in the browser, and most of them do not support training. Those that do 
usually only have experimental support for WebGPU. We could implement 
backpropagation from scratch, but because browser performance falls short of 
desktop performance, we instead decided to implement a WebSocket server that runs
training in PyTorch.

\begin{figure}[!b]
    \centering
    \input{figures/server}
    \caption{
        Sequence diagram of message passing between the browser and the
        training server during online training. When the connection is
        established, a new model is created. Received ground truth data are
        used for training, while the final model weights are obtained using a
        separate message type.
    }
    \label{fig:server}
\end{figure}

The main protocol between the browser and the server is illustrated in
\Cref{fig:server}. When the browser establishes a new connection to the server,
a new model instance is initialized. After the browser receives confirmation
that the model is ready, the user can enable the \emph{train} option to start 
sending ground truth data. This data is sent on every frame, except when data is
still being copied. Instead of storing the bytes in a ZIP archive as before, they 
are now sent directly to the server with the \emph{ground-truth} header. The
server first parses and preprocesses the data. It removes empty pixels, invalid 
angles, and out-of-bounds coordinates, while normalizing the angles to the unit
interval. A single training step is performed, and the validation loss is returned 
to be displayed in the browser. When the user enables the \emph{predict} option,
a \emph{model-request} message is sent to the server. The server responds by 
creating a ZIP archive of the model weights, which is sent as bytes in a message
to the browser.

Model training can be restarted either by reconnecting to the server or by using
a separate \emph{model-reset} message type. This allows us to restart training if
the model gets stuck in a poor local minimum. To prevent this during evaluation,
we added support for setting the seed using a special message sent at the start
of evaluation to make it reproducible. Model resetting is also performed each
time the VPT configuration is changed, since the model is trained for a specific
configuration.

\section{Bilateral filter}

Since our ground truth data values are generated from the camera view, we can
imagine them as forming a 2D image. This is only an approximation, because the
generated samples do not hit the volume at the same depth, meaning the actual
image plane is not flat. However, this still allows us to apply some image
filtering methods to our ground truth data before handing it off for training.
In this case, we propose that the model can learn this filtering, which could be
beneficial if the filtering algorithm is computationally more demanding.

In our approach, we use the \emph{bilateral filter} for this use
case~\cite{paris_gentle_2007}. It is similar to Gaussian filtering but preserves
edges by weighting neighbors not only by their distance but also by their color
difference. It has three parameters: $\sigma_k$, $\sigma$, and a threshold $\tau$.
For each pixel with color $\mathbf{c}$, we consider neighbors with colors
$\mathbf{c}_n$ in the neighborhood with radius
\begin{equation}
    r = \sigma_k \cdot \sigma.
\end{equation}
If the pixel is not a background pixel, we compute the spatial weight
\begin{equation}
    w_d = \exp\left(-\frac{dx^2 + dy^2}{2\sigma^2}\right),
\end{equation}
and the range weight
\begin{equation}
    w_r = \exp\left(-\frac{\norm{\mathbf{c} - \mathbf{c}_n}}{2\tau^2}\right).
\end{equation}
We then multiply these weights and use the result to compute the weighted average
over the entire neighborhood. A comparison between the filtered and unfiltered
images is shown in \Cref{fig:filter}.

\section{Neural render}

All components described in the previous sections come together to form the
algorithm we call \emph{neural render}. It is based on path tracing, with
indirect radiance computation replaced by neural network inference.

Path tracing is described in \Cref{alg:pt}. A shader first generates sample
points, which are then used to compute both direct and indirect radiance. If
filtering is enabled, we apply it to both. If frame accumulation is disabled,
previous radiance values are discarded; otherwise, they are updated with the
newly computed values. The final image depends on the current display mode
(global illumination, direct radiance, or indirect radiance). After rendering
is complete, the resulting indirect radiance values are sent to the training
server.

The neural render described in \Cref{alg:nr} follows similar steps. We still
generate sample points and compute direct radiance in the same way, but now the
indirect radiance is computed using a neural network, so the volume data is no
longer needed. If filtering is enabled, the model is already trained on filtered
data, so we only have to filter the direct radiance. The remaining steps stay
the same, except for sending data to the training server. Because we no longer
compute indirect radiance values, we do not have ground truth values to send to
the server.

The model forward pass is implemented in a WebGPU shader, so the data stays on
the device for the entire iteration. Before neural rendering starts, the model
weights received from the server are copied to buffers on the \ac{gpu}. We
process all samples for a single pixel in the same shader invocation. To simulate
transparency, which is the result of delta tracking in path tracing, we introduce
an additional rejection of some samples. We toss a coin and reject samples with
probability $P_n(\mathbf{x})$, which is already computed and stored in the sample
generation shader.

\begin{algorithm}
    \caption{Path tracing}
    \label{alg:pt}
    \DontPrintSemicolon
    \KwIn{%
        volume $\mathcal{V}$,
        camera $\mathcal{C}$,
        configuration $\gamma$,
        radiance $L$}
    \KwOut{rendered image $I$, updated radiance $L$}
    \BlankLine
    
    $\mathbf{X}, \boldsymbol\Omega \leftarrow$ GenerateSamplePoints(%
        $\mathcal{V}$, $\mathcal{C}$, $\gamma$)\;
    $L_d \leftarrow$ ComputeDirectIllumination(%
        $\mathcal{V}$, $\gamma$, $\mathbf{X}$, $\boldsymbol\Omega$)\;
    $L_i \leftarrow$ ComputeIndirectIllumination(%
        $\mathcal{V}$, $\gamma$, $\mathbf{X}$, $\boldsymbol\Omega$)\;
    \BlankLine

    \If{filtering enabled}{
        $L_d, L_i \leftarrow$ ApplyBilateralFilter($L_d$, $L_i$, $\gamma$)\;
    }
    \If{not accumulate}{
    $L \leftarrow \mathbf{0}$\;
    }
    \BlankLine
    
    $L \leftarrow$ AccumulateRadiance($L$, $L_d$, $L_i$)\;
    $I \leftarrow$ ComposeImage($L$, $\gamma$) \;
    TrainServerSend(\texttt{"ground-truth"}, $L_i$)\;
    \BlankLine
    
    \Return{$I$, $L$}
\end{algorithm}

\begin{algorithm}
    \caption{Neural render}
    \label{alg:nr}
    \DontPrintSemicolon
    \KwIn{%
        volume $\mathcal{V}$,
        camera $\mathcal{C}$,
        configuration $\gamma$, radiance $L$,
        model $\mathcal{N}$}
    \KwOut{rendered image $I$, radiance $L$}
    \BlankLine

    $\mathbf{X}, \boldsymbol\Omega \leftarrow$ GenerateSamplePoints(%
        $\mathcal{V}$, $\mathcal{C}$, $\gamma$)\;
    $L_d \leftarrow$ ComputeDirectIllumination(%
        $\mathcal{V}$, $\gamma$, $\mathbf{X}$, $\boldsymbol\Omega$)\;
    $L_i \leftarrow$ PredictIndirectIllumination(%
        $\mathcal{N}$, $\mathbf{X}$, $\boldsymbol\Omega$)\;
    \BlankLine
    
    \If{filtering enabled}{
        $L_d \leftarrow$ ApplyBilateralFilter($L_d$, $\gamma$)\;
    }
    \If{not accumulate}{
    $L \leftarrow \mathbf{0}$\;
    }
    \BlankLine

    $L \leftarrow$ AccumulateRadiance($L$, $L_d$, $L_i$)\;
    $I \leftarrow$ ComposeImage($L$, $\gamma$)\;
    \BlankLine
    
    \Return{$I$, $L$}
\end{algorithm}
